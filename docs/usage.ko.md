# BANDIT · 밴딧 사용법

[English](usage.md) · [설치](../INSTALL.md) · [예제](../examples/README.md)

프로젝트 폴더에서 한 줄로 설치하세요. 필요하면 새 에이전트 세션을 여세요.

```sh
npx --yes https://github.com/ch4570/bandit/releases/download/v0.4.0/bandit.tgz
```

한 번 설치하면 전문 스킬 4개와 통합 `$bandit` 스킬이 추가됩니다. 아래에서 작업에 맞는 명령어를 고르고 원하는 결과를 적으세요. 여러 작업을 함께 맡기려면 `$bandit`을 사용하면 됩니다. 기존 기획서와 근거 자료, 이번에 정할 결정, 답을 바꿀 제약을 함께 주면 좋습니다. 제안만 받을지, 읽기 전용 검토인지, 특정 문서를 수정할지도 알려주세요.

**0.2 또는 0.3에서 업그레이드:** 같은 프로젝트에서 위 0.4.0 설치 명령을 실행한 뒤 새 에이전트 세션을 여세요. 기존 `--global`이나 경로 옵션은 그대로 붙이세요. [이전 버전에서 옮기기](../INSTALL.md#upgrade-from-02-or-03)

밴딧은 분명하고 실용적인 말투로 기획합니다. 서부식 표현이나 역할극을 요청에 섞지 않아도 됩니다.

## 문제 조사와 가정 검증 · `$bandit-research`

```text
$bandit-research 경쟁사 기능 페이지 2개만 있고 고객 인터뷰는 아직 없어.
공동 일정 앱의 기회 요약을 1쪽으로 써줘. 자료에서 확인한 사실과
사용·지불에 대한 가정을 구분하고, 개발 여부를 바꿀 가장 작은
다음 실험을 제안해줘.
```

각 출처가 무엇을 뒷받침하는지, 무엇이 아직 미확인인지, 다음 결정에 필요한 실험을 받습니다. 무료 가입은 관심의 근거가 될 수 있지만 유료 구매를 검증하지는 않습니다. 부족한 조사 자료를 가상의 인터뷰나 시장 수치로 채우지 않습니다.

실시간 검색 도구가 없으면 제공된 자료를 검토하고 조사 계획을 만들 수 있습니다. 확인하지 못한 사실은 미확인으로 남깁니다. 제안한 성공 기준과 실제 달성한 결과도 구분합니다.

[스킬 지침](../skills/bandit-research/SKILL.md).

## MVP 범위 결정 · `$bandit-scope`

```text
$bandit-scope P0가 11개인 이 기획을 1인 개발 2주 유료 파일럿으로 줄여줘.
변경 요청을 보내고 지정 고객이 확인한 결과를 찾는 흐름은 유지해.
수동으로 대신할 부분과 뒤로 미룰 기능의 이유도 써줘.
```

첫 사용을 끝낼 수 있는 범위, 선택의 이유, 작업량 가정을 받습니다. P0를 무조건 다섯 개로 맞추는 방식은 쓰지 않습니다. 확인 권한·대상 버전·중복 처리 같은 조건은 기능을 신뢰할 수 있게 만드는 일부이므로 편의 기능과 같은 방식으로 잘라내면 안 됩니다.

[스킬 지침](../skills/bandit-scope/SKILL.md).

## 기획서 작성·재작성 · `$bandit-specify`

```text
$bandit-specify 5명이 쓰는 투표 규칙을 개발 명세로 정리해줘.
A 2표, B 2표, 미응답 1명에서 누가 언제 확정할 수 있는지,
자기 표 변경과 재논의를 시작하면 무엇이 남는지 구체화해줘.
```

역할·대상·조건·상태 변경·예외·수용 시나리오를 정리합니다. 빠진 결정을 드러내고, 초안 선택을 위임받았다면 이유 있는 권고안을 만듭니다. 권고가 이미 채택된 정책처럼 보이지 않게 구분합니다. 공통 등록·수정·삭제 목록만으로 투표나 확인의 의미를 대신하지 않습니다.

동작을 이해하는 데 필요한 최소 데이터 관계는 설명할 수 있습니다. 데이터베이스나 API를 임의로 고르거나 기존 아키텍처를 바꿀 필요는 없습니다.

기존 기획서를 새 방향에 맞춰 다시 쓸 때도 같은 명령어를 사용합니다.

```text
$bandit-specify 유료 개인 플랜을 무료 공유 작업공간으로 바꾸기로 했어.
docs/PRD.md를 새 방향에 맞춰 다시 써줘. 필요한 문서 구조와 규칙은
재구성하고, 권한·첫 사용·지표·수용 기준을 일관되게 정리해줘.
이전 파일럿 결과는 당시 가격과 조건을 붙여 보존해줘.
```

요청한 범위에 맞춰 내용과 구조를 다시 작성하고, 변경된 규칙과 연결된 지표·실험·검증 항목을 함께 정리합니다. 영향을 받지 않은 확정 결정과 과거 관측의 의미는 유지합니다. 새 방향을 과거 실험이 검증한 것처럼 바꾸지 않습니다.

[스킬 지침](../skills/bandit-specify/SKILL.md).

## 원본을 바꾸지 않는 검토 · `$bandit-review`

```text
$bandit-review docs/PRD.md의 갱신 실험만 검토해줘.
구독자 5명이 계속 쓰겠다고 했지만 다음 결제일은 아직 안 왔어.
원래 성공 기준을 유지해서 판정하고 파일은 수정하지 마.
```

상황·기대 규칙·근거·영향·수정 제안을 좁은 범위로 받습니다. 이미 잘 정해진 규칙을 빠졌다고 지적하지 않습니다. 갱신 의향과 실제 갱신 결제는 다른 사건이며, 관찰일이 오지 않은 고객은 아직 미측정입니다.

기획서를 읽었다고 제품을 실행한 것은 아닙니다. 코드 읽기·스크린샷·로컬 시연·테스트 통과·실제 고객 성과가 각각 무엇을 확인했는지 구분합니다.

[스킬 지침](../skills/bandit-review/SKILL.md).

## 출시 예정: 조사·기획·마케팅·제품 설계·BM 연결

**현재 브랜치의 미출시 지침입니다.** 문서 위쪽의 v0.4.0 명령은 공개된 릴리스를 설치하며, 이 절에서 설명하는 새 [제품 여정 지침](../skills/bandit/references/product-journey.md)은 포함하지 않습니다. 명령어는 기존 5개를 유지합니다.

여러 단계를 함께 요청하면 `$bandit`이 조사 → 제품 기획 → 마케팅 → 제품 설계 전달 → 비즈니스 모델(BM)을 연결하고, 문서들이 같은 제품과 제공 조건을 설명하는지 확인합니다. 모든 요청에 이 순서를 강제하지는 않습니다. 잠정 가격과 제공 한도를 먼저 두어 마케팅과 설계에 반영하고, 뒤에서 얻은 결과가 달라지면 관련 범위·문구·흐름·검증 항목을 다시 조정합니다.

아래는 가상 상황의 예시입니다. 아이디어·제약·문서 경로를 실제 자료에 맞게 바꾸세요.

```text
$bandit 제공된 자료로 프리랜서용 변경 요청 승인 서비스의 가능성을 검토해줘.
1인 개발 2주 MVP를 추천하고, 마케팅 기획안, 제품 흐름·콘텐츠·텍스트
와이어프레임, 비즈니스 모델을 연결해줘. 가격·비용·처리량 가정을 명시하고,
고객·약속·제공 조건을 일관되게 맞춰줘. 제안한 선택과 미확인 주장을
구분하고, 다음 판단에 필요한 실험을 제안해줘.
```

요청한 깊이에 맞춰 다음 산출물을 연결합니다.

| 작업 | 전달할 내용 |
| --- | --- |
| 조사 | 고객·대안·제공 조건의 근거, 출처와 관측 조건, 미확인 가정 |
| 제품 기획 | 처음부터 끝까지 완결되는 결과, 포함·보류 범위, 제공 한도, 수용 시나리오 |
| 마케팅 | 포지셔닝, 제목·보조 문구, 행동 유도 문구, 대상·담당자·기간·처리량·지출 한도·판단 기준을 갖춘 채널 실험 |
| 제품 설계 | 과업 흐름, 화면·콘텐츠 순서나 텍스트 와이어프레임, 보이는 제공 조건, 필요한 상태·복구·접근성, 프로토타입 검증 계획 |
| 비즈니스 모델 | 고객과 지불자, 과금 단위, 제공 업무·자원, 가격·비용 가정, 공헌이익·처리량 계산, 다음 실험 |

고객·약속·이용 자격·가격과 단위·제공 시점·처리량·취소 조건을 일관되게 맞춥니다. 손익분기점에 필요한 판매량을 실제로 도달 가능한 수요와 제공 가능한 처리량 양쪽에 대조합니다. 가정으로 계산한 수치는 추정이며, 문서가 일관된다고 유료 수요가 검증된 것은 아닙니다. 제품 설계 기획안은 무엇을 프로토타입으로 만들고 확인할지 설명하며, 렌더링이나 테스트가 끝난 화면을 뜻하지 않습니다.

결정에 영향을 주는 예산·수수료·처리량·경제성의 산출값은 사용 가능한 계산
도구로 확인하고, 방법과 실제 반환값을 짧게 남깁니다. 공식만 적었다고
실행이 증명되지는 않습니다. 계산이 금지되거나 생략된 경우, 또는 도구가 없으면
검증은 미완료로 남깁니다. 코드 실행 금지는 제품 코드뿐 아니라 산술 계산 코드에도
적용됩니다. 허용된 비코드 계산 도구를 쓰거나 확인하지 못한 계산을 밝힙니다.
출처의 숫자를 인용하거나 정성적인 질문에 답할 때
불필요한 계산을 만들지 않습니다.

기간이 정해진 상품은 판매·청구 시점과 실제 제공·지원 기간, 자원 확보 기간,
관찰 기간을 구분합니다. 마지막으로 받는 고객까지 약속한 서비스를 제공할 수
있는지 확인합니다. 확보한 마지막 작업 시간부터 역산하고, 고객이 결과를 검토한
뒤 포함된 후속 질문이나 확인 절차를 실제로 사용할 시간이 있는지 순서대로
대조합니다. 허용한 지연 제출과 명시된 고객의 참여 가능 시간도 포함합니다.
동시 시작 고객과 후속 응답의 처리량은 실제로 남은 약속 시간대에 맞춥니다.
자원이 부족한 기간은 계약 전 확보 조건으로 남기거나 영향을 받는 제공 조건을
함께 조정합니다. 이후 운영 자원이 이미 확보되어 있다면 준비
기간이 짧다는 이유만으로 서비스 기간을 줄이지 않습니다.

서비스를 줄여도 원가의 원래 청구 기간은 유지합니다. 일할·기간 비례 과금이
확인됐을 때 적용하고, 미확인 금액은 청구 조건을 확인할 별도 시나리오로 둡니다.
고객당 비용의 모든 항목은 같은 고객 수와 기간을 기준으로 계산합니다. 실험이나
신규 접수를 중단하더라도 기존 고객의 제공·복구·종료 조건은 따로 정해야 합니다.
고객이 참여할 수 있는 시간은 메시지 수신뿐 아니라 가입·결제·필수 보완에도
일관되게 반영합니다.

일부만 필요하면 해당 전문 스킬을 바로 사용하세요.

제품의 제공 조건을 판단할 근거 조사:

```text
$bandit-research 프리랜서용 승인 서비스의 고객 메모와 경쟁사 페이지를 검토해줘.
어떤 고객·약속·채널·가격 가정을 뒷받침하는지 알려줘. 출처 날짜와 제공
조건을 유지하고, 관심과 결제를 구분해줘. 가장 중요한 미확인 가정을
검증할 실험 하나를 제안하고, 근거 요약만 작성해줘.
```

기존 기획서를 바탕으로 UX·사업 기획안 작성:

```text
$bandit-specify docs/PRD.md를 바탕으로 유료 파일럿의 UX·사업 전달 자료를 써줘.
포지셔닝 문구와 채널 실험, 진입부터 승인까지의 흐름, 화면·콘텐츠 순서와
텍스트 와이어프레임, 이용을 결정하는 시점의 가격·취소 조건, 필요한
실패·복구 상태를 포함해줘. BM에는 지불자·제공 업무·비용·처리량을 연결해줘.
초안 선택을 표시하고 수용 시나리오를 붙여 docs/PRD.md에 작성해줘.
```

같은 제품과 제공 조건을 설명하는지 문서 간 검토:

```text
$bandit-review docs/PRD.md, docs/marketing.md, docs/design-brief.md,
docs/business-model.md에서 고객·약속·이용 자격·가격과 단위·제공 한도·취소
조건이 충돌하는지 검토해줘. 고객 한 명이 홍보 문구에서 사용·제공·결제까지
이어가는 경로와 복구 사례 하나를 확인해줘. 결정을 바꿀 계산을 다시 확인하고,
각 충돌의 위치·영향·수정 제안을 적어줘. 원본 문서는 수정하지 마.
```

제공 범위를 정하거나 줄이는 작업은 계속 `$bandit-scope`에 맡깁니다. 마케팅·설계·BM 명령어를 추가하지 않습니다. 기획안을 요청했다고 홍보 문구 게시·고객 연락·지출·화면 구현·실험 실행까지 허용한 것은 아닙니다. 이런 행동은 별도로 요청한 작업 범위에서 실행합니다.

## 요청 크기에 맞는 결과

지정한 전문 스킬에서 바로 시작합니다. 조사·범위 결정·명세·검토를 모두
거치는 고정 순서는 없습니다. 요청에 적힌 입력 자료·산출물·완료 조건과
시간·탐색 한도를 활용하며 별도 양식을 다시 요구하지 않습니다.
작업 범위는 자연어로 정할 수 있습니다.

```text
$bandit-review docs/PRD.md와 docs/approval-policy.md에서 권한·중복 요청·실패
복구만 검토해줘. 원본은 수정하지 마. 각 발견을 판단하는 데 필요한 링크를
확인하고 위치·발생 조건·영향·수정 방법을 적어줘.
결론을 바꿀 수 있는 미확인 사항은 따로 표시해줘.
```

선택한 지침은 빠짐없이 읽고, 무관한 참조는 미리 모두 읽지 않습니다.
요청한 검증이 끝나면 결정을 바꾸지 않는 불확실성 때문에 탐색을 계속하지
않습니다. 요청 변경·중대한 충돌·오래된 출처·검증 실패가 있으면 영향을 받는
범위를 다시 확인합니다. 필요한 권한·복구·근거 확인은 생략하지 않습니다.
지정한 한도에 도달하면 확인된 결과와 남은 일을 구분합니다.
프롬프트의 시간·탐색 한도는 provider의 과금 차단 장치가 아닙니다.

짧은 결정은 문단이나 작은 표로 끝낼 수 있습니다. 계속 사용할 기획은 기존 문서 안에서 중요한 근거·결정·요구사항·확인 방법을 연결합니다. 식별자와 선택적 템플릿은 추적에 도움이 될 때만 사용합니다.

사용자가 채택한 목표와 코드에서 읽은 현재 동작도 나눕니다. 기획은 소유자만 수정하도록 정했는데 코드가 모든 로그인 사용자에게 허용한다면 불일치를 보고합니다. 구현을 맞는 것으로 보이게 하려고 목표를 바꾸지 않습니다.

## 구현·UI 담당에게 전달

사용자 역할, 핵심 과업, 확정·제안 결정, 상태 조건, 실패·복구, 저장 범위, 수용 시나리오를 전달합니다. 이후 화면 구성·피드백·문구를 해당 규칙에 맞춰 다듬을 수 있습니다.

별도 UI 스킬, Figma, 이슈 관리 도구, 외부 계정이 필수는 아닙니다. 기획 요청만으로 코드 변경·고객 연락·티켓 게시·배포를 실행하지 않습니다. 별도로 요청한 행동에는 호스트의 기존 권한을 따릅니다.

[설계](design.md), [평가](../evals/README.md), [실제 검증 기록](../VALIDATION.md)에서 범위와 확인 방법을 볼 수 있습니다.
