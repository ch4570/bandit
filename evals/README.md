# Development evaluations

BANDIT is evaluated on concrete planning work, separately from installer and
package checks. Inputs are fictional, and all claimed observations inside them
are supplied fixture data. They are not real customer results.

Some local engineering records use [public path placeholders](PUBLICATION.md).
Their original receipt hashes remain original; the publication manifest maps
them to normalized public-copy hashes without changing run outcomes or grades.

adds installation and preservation evidence, not new planning executions.

## Forward-test method

An independent agent receives only the user's request, raw fixtures, and the
skill with its relevant references. It receives no rubric, desired answer,
suspected defect, or previous output. Product inputs stay read-only by default.
An explicitly enabled live-source task may also research the public sources
authorized by its request; other cases keep browsing disabled.
The optional `--edit-artifact` run uses a writable workspace and instructs the
agent to edit only the named input artifact; before/after hashes check whether
it respected that scope. No customer outreach or live experiment is run.

For paired diagnostic runs, each condition receives the same case and output
cap in a fresh Codex CLI task:

1. Baseline reasoning without a PM skill.
2. [phuryn/pm-skills](https://github.com/phuryn/pm-skills/tree/18468a95b427e70e258b51389796367c6f684e7d)
   at the pinned commit, with relevant command procedures and referenced skills.
3. The instruction snapshot under test (PM Craft in the historical record,
   BANDIT in current runs).

The CLI adaptation reads slash-command instructions as text and applies the
actual user's scope first. The complete upstream checkout is available for
referenced dependencies; we do not compare against an isolated skill while
withholding the workflow that gives it essential context.

## Run a case yourself

The runner uses your installed, authenticated Codex CLI and its normal account
usage. It is opt-in and is not part of the default CI tests. Repository tools
need Python 3.11+. Installations of Codex with different CLI flags may require
adapting the runner; the recorded runs identify the CLI version.

```sh
python3 evals/run_local.py --case 04-incomparable-scores --arm bandit-scope --output-dir /absolute/path/to/new-runs
python3 evals/run_local.py --case 04-incomparable-scores --arm baseline --output-dir /absolute/path/to/new-runs
```

Specialist arms are `bandit-research`, `bandit-scope`, `bandit-specify`,
and `bandit-review`. These copy all five skill folders into
the isolated project's `.agents/skills/` and invoke the selected `$bandit-*`
name in the prompt. Inspect the execution log to confirm the agent read that
entrypoint. The general `bandit` arm retains the explicit instruction snapshot
method used by the earlier runner.

To test a specialist with no sibling skills available, add `--standalone`:

```sh
python3 evals/run_local.py --case 09-linked-policy-review --arm bandit-review --standalone --output-dir /absolute/path/to/new-runs
```

Only that specialist's complete folder is copied, including its transitive
references. The metadata records this layout. New fixture directories containing
`request.md` are discovered automatically. Upstream runs require a reviewed
workflow mapping; the runner refuses unmapped cases instead of selecting a
bare skill as a substitute for the upstream workflow.

To check a real artifact rewrite, permit the PRD named in case 06:

```sh
python3 evals/run_local.py --case 06-existing-spec-rewrite --arm bandit-specify --edit-artifact input/docs/PRD.md --output-dir /absolute/path/to/new-runs
```

The runner retains the original input files separately. Review the resulting
PRD and the before/after hashes, not just the agent's final reply.
New runs also retain original instructions and inputs for read-only tasks,
so an unexpected modification does not destroy the starting evidence.

### Optional model request

Omitting `--model` preserves the existing host-default behavior with
`--ignore-user-config`. To request a model for one run, replace the literal
`MODEL_ID` placeholder below with an identifier accepted by your CLI/account:

```sh
python3 evals/run_local.py --case 09-linked-policy-review --arm bandit-review --standalone --model MODEL_ID --output-dir /absolute/path/to/new-model-runs
```

The runner passes the exact identifier as one `codex exec --model` argument;
the [official CLI reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli)
documents this per-run override. Use a nonempty identifier without whitespace,
control characters or a leading `-`. Availability is determined by the CLI and
account; the runner does not consult a model catalog or retry with a fallback.

Once a run is staged, `metadata.json` records the requested string in
`model_override` and the exact command, including version-probe, launch and
completed child failures. Invalid identifiers are rejected before staging.
Omission remains `null`. These fields
record a request, not verified backend identity: an alias is not an immutable
backend snapshot, and other host settings and external services remain unpinned.
The override alone does not make a run reproducible or a model comparison valid.
This example is not a recorded TASK. Earlier runs retain their original metadata;
do not retroactively label them as explicit-model runs.

### Stage an artifact sequence

Case 12 uses `--fixture-dir` to expose only the current stage's raw files:

```sh
python3 evals/run_local.py --case 12-access-transition-1 --fixture-dir evals/sequences/12-access-transition/stage-1 --arm bandit-specify --standalone --edit-artifact input/docs/PRD.md --output-dir /absolute/path/to/new-runs
```

Wait for completion and archive the run before proceeding. Copy its actual
`workspace/input/` tree into a new staging directory, then overlay the files
from `evals/sequences/12-access-transition/stage-2/`. This replaces the request
and adds the new raw decisions/checks while preserving the resulting PRD and
earlier evidence exactly. Do not repair, summarize, or replace the PRD with an
expected answer. Run the second task with that staged directory:

```sh
python3 evals/run_local.py --case 12-access-transition-2 --fixture-dir /absolute/path/to/staged-input --arm bandit-specify --standalone --edit-artifact input/docs/PRD.md --output-dir /absolute/path/to/new-runs
```

Keep the skill sources unchanged between stages. Verify that stage 1's final
PRD hash equals stage 2's initial PRD hash and that both instruction snapshots
match. Each stage is a fresh agent with no later-stage inputs or rubric; this
tests artifact carry-forward, not conversation memory. A custom fixture must
contain `request.md`, contain no linked files, and not overlap its run output.
Custom fixtures have no upstream workflow mapping and cannot use that arm.
The output run directory also must not overlap the selected instruction source.
Instruction resources must be ordinary files/directories, without nested
symlinks; this prevents copied links from reintroducing recursive output paths.
Every regular file in the chosen fixture tree is copied: maintainers must
exclude rubrics, diagnoses and future inputs themselves. Staging plus prompt
restrictions is not a security boundary against all external filesystem reads;
inspect the actual trace as well as the copied file inventory.

### Public-source research

Only enable web research when the task authorizes it. Case 14 permits public
reading without accounts, installation, purchases, contact or external writes:

```sh
python3 evals/run_local.py --case 14-live-source-research --arm bandit-research --standalone --web-search live --output-dir /absolute/path/to/new-runs
```

The runner's default is `--web-search disabled`. It now explicitly configures
Codex's `web_search` setting; earlier archives instructed no browsing but left
that tool setting to the host. Do not retroactively label those older runs
tool-disabled. Live mode uses the supported config override documented in the
[official CLI reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli).
It does not enable shell networking or change the existing sandbox choice.
Omit `--edit-artifact` for this read-only research task.

Metadata records the requested web mode and UTC start/finish times. Inspect
events for actual retrieval attempts and grade whether citations support the
attached claims. Tool availability and process completion are not evidence
that every cited page was successfully read. CLI events can omit returned
page bodies or details of batched opens; retain that limitation. A later source
recheck can assess then-current support, but cannot reconstruct the exact
page text the task saw. Live pages and host services are not frozen fixtures.
Keep missing access, ambiguous conditions and conflicting sources visible.

For upstream, use a clean checkout at the pinned commit:

```sh
git clone https://github.com/phuryn/pm-skills.git /absolute/path/to/upstream
git -C /absolute/path/to/upstream checkout 18468a95b427e70e258b51389796367c6f684e7d
python3 evals/run_local.py --case 04-incomparable-scores --arm upstream --upstream /absolute/path/to/upstream --output-dir /absolute/path/to/new-runs
```

Each run preserves the prompt, input and instruction hashes, final output,
events, error output, exit code, and elapsed time. Existing run directories are
never reused. Review full outputs against the applicable rubric or case request
before revising the skill. Report partial results and failed runs alongside
successes.

Distinguish an incorrect claim, a missing decision-relevant condition, and an
omitted comparison requested only by a rubric. A partial score alone does not
establish an instruction defect. For new rubrics, state before execution which
meaning must be present and accept equivalent counts or prose unless the task
requires a particular artifact. Preserve old criteria and grades when a later
audit exposes ambiguity; document the limitation instead of silently rescoring.

## Archive a completed run

```sh
node evals/archive_run.mjs /absolute/path/to/new-runs/09-linked-policy-review--bandit-review evals/results/my-new-run
```

The destination must not exist. The helper verifies metadata against actual
input and instruction hashes before creating an archive. It keeps original
fixtures under `input/`, edited artifacts under `after/`, and instruction text
under `instructions/`. It records PNG hashes instead of copying those images.
Final-summary relative links retain their task-time form. For an edited
artifact, inspect `after/`; a summary's `input/` link now points to the preserved
original, not the rewritten file.
Only prompt, output, events, stderr and metadata receive literal temporary-path
normalization; provenance records both original and archived hashes.

Completed failures and incomplete responses are retained with explicit status.
Version-probe and task-launch errors are retained as terminal runner failures,
with error details and a null child exit code rather than an invented process
result. A still-running or contradictory metadata state is not made terminal
merely by requesting an archive.
Successful archival is not a successful task or a quality grade. Older runs
with missing original bytes are identified as incomplete evidence; available
after-state is retained without pretending it was the original. New runs keep
the originals automatically. Restore the instruction tree at the location
recorded by `instruction_restore_directory` when replaying an archive, including
any hash-only PNGs needed for an identical workspace.

Inspect the logs before sharing: path normalization is not a secret scrubber.
Use synthetic or sanitized inputs, and retain failed outputs before revising
instructions or rubrics.

## Interpretation limits

Case 14 adds a focused public competitor-source check, not fresh customer
research or a general market-research benchmark. These tasks do not test real
stakeholder negotiation, longitudinal decisions, enterprise strategy, games,
or statistical expertise.
One run per condition cannot measure reliability or establish causal performance
differences. Host-default model settings and shared-system overhead also limit
comparisons of usage and elapsed time. A correct baseline is evidence that the
model can already perform that task; it is not a reason to hide its result.

See [Validation](../VALIDATION.md) for packaging checks and [Comparison](../docs/comparison.md)
for the narrower, source-based design claims.
