**ShelfNote 첫 배포 추천·개발 인계안 — 2026-09-09**

**D1 — 텍스트 제보 → 책임자 처리 기록 → 제보자 결과 확인을 하나의 배포 범위로 추천합니다.** 대상은 창고 한 곳의 주간 직원 12명과 현재 교대 책임자입니다.

근거는 [brief.md](input/brief.md)의 채택된 방향·작업 환경·추정치입니다. 비공개 스프레드시트 때문에 직원이 처리 상태를 다시 묻는 상황을 해결합니다. 자료는 가상 입력이며 실제 수요나 구현 성과의 증거는 아닙니다. [draft.md](input/draft.md)는 미채택 화면 제안으로, 이번 명세에서는 지도 중심 홈을 제보·처리 흐름으로 대체합니다.

- **포함:** 선반 검색, 텍스트 제보, 내 제보, 책임자 미해결 목록·상세·처리 완료 기록.
- **유지:** 기존 로그인, 직원·선반 디렉터리, 공유 저장소, 모바일 폼.
- **보류:** 사진, 오프라인 전송함, 이메일 알림, 지도, 대시보드, 배정·기한·댓글·수정 이력. 핵심 흐름에 필수가 아닙니다.
- **제외:** 긴급 상황, 재고 수량·구매·설비 관리, 공개 링크, 신규 가입.
- **대안:** 기존 메시지·스프레드시트는 개발 없이 계속 쓸 수 있지만 직원의 직접 결과 확인을 충족하지 못합니다. 사진 포함안은 점검까지 4.5일로 한도를 넘습니다.

계산은 제보·내 목록 1.5일 + 책임자 처리 1일 + 현장 흐름 점검 0.5일 = **3 개발일**입니다. 4일 중 남은 1일을 필수 복구 동작과 수정 여유로 둡니다. 아래 재시도·동시 처리 보장이 기존 추정에 포함됐는지는 미확인으로, 납기를 확정하지 않습니다.

**개발 명세 — R1~R5는 D1에 연결됩니다.** 세부 길이·정렬·재시도·변경 제한은 추천 정책입니다.

| ID | 규칙과 관찰 가능한 결과 |
|---|---|
| R1 권한 | 서버에서 활성 직원 여부와 현재 역할을 확인합니다. 직원은 생성 및 자기 제보 조회만, 현재 책임자는 창고 전체 조회·완료 기록이 가능합니다. 역할 교체 시 미해결 제보가 새 책임자에게 보입니다. 이전 책임자는 일반 직원 권한으로 돌아가고, 퇴사자는 직접 주소를 포함한 모든 접근이 차단됩니다. |
| R2 제보 객체 | 제보 ID, 창고, 유효한 선반 ID, 설명, 제보자 직원 ID, 서버 생성 시각, 상태를 저장합니다. 완료 시 처리 내용·처리자 ID·완료 시각을 추가합니다. 상태는 **미해결 → 해결됨**뿐이며, 열람은 상태를 바꾸지 않습니다. 기록은 책임자 개인에게 귀속되지 않습니다. |
| R3 제출·복구 | 선반 검색 결과를 선택하고 공백 제외 1~1,000자 설명을 입력합니다. 저장 시 선반 유효성을 재확인합니다. 영구 저장 확인 후에만 제보 번호와 ‘미해결’을 표시합니다. 실패·결과 불명확 시 입력을 유지하고 재시도를 제공합니다. 같은 제출의 재시도는 동일 요청 식별자를 사용해 기존 제보를 반환하며 중복 생성하지 않습니다. 연결 복구 후 사용자가 재시도하며 자동 오프라인 전송은 없습니다. |
| R4 처리 | 책임자 미해결 목록은 오래된 순입니다. 상세에서 현장 조치를 확인한 뒤 1~1,000자 처리 내용을 입력하고 명시적으로 완료합니다. 내용·처리자·시각·상태는 함께 저장됩니다. 실패하면 완료로 표시하지 않고 입력을 유지합니다. 반복·동시 완료는 최초 저장 결과를 유지하고 후속 요청에 이미 완료된 내용을 보여줍니다. 소프트웨어가 현장 조치를 검증하지는 않습니다. |
| R5 결과 확인 | 내 제보는 최신순으로 선반·설명·상태·접수 시각을 표시합니다. 상세에서 처리 내용·완료 시각을 확인합니다. 진입·새로고침 시 서버 상태를 읽고 조회 실패와 빈 목록을 구분합니다. 첫 배포에는 수정·삭제·재개가 없으며 재발은 새 제보로 접수합니다. |

**인수 확인 계획:** 구현된 시험 버전과 작업용 휴대폰 브라우저에서 아래를 확인하고 버전을 기록합니다. 모두 **계획됨·결과 미관찰**이며, 구현·제품 테스트·현장 점검은 실행하지 않았습니다.

- R2~R5: 직원 제출 → 재접속 후 저장 확인 → 책임자 열람에도 미해결 유지 → 완료 기록 → 직원 새로고침 후 처리 내용 확인.
- R3~R4: 저장 직후 응답 유실·재시도에도 제보 하나만 존재하고, 중복 완료가 최초 기록을 덮어쓰지 않음.
- R1: 다른 직원 제보 접근 차단, 책임자 교체 반영, 퇴사자 접근 차단.
- R3~R5: 잘못된 선반·빈 입력·통신 실패에서 오류와 복구 경로 확인.

다음 단계는 개발자가 공유 저장소의 중복 방지·원자적 완료 지원과 공수를 먼저 확인하는 것입니다. 4일을 넘으면 핵심 복구를 삭제하지 않고 첫 사용을 연기합니다. 반일 점검에서는 직원의 결과 확인과 책임자의 교대 인계를 확인하며, 실제 반복 사용 가치는 시험 이후 판단합니다.
