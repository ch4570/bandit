## 03: policy authority, explicit acceptance, and changed terms

**Authority is correctly resolved.** `master.md:3–5` explicitly names `approval-policy.md` as adopted and says no later decision replaces it. `generated-prd.md:3–4` identifies itself as implementation-derived and unadopted. Thus the later PRD date does not supersede the adopted policy. `output.md:1` correctly follows that authority rather than treating code/PRD agreement as independent validation.

1. **Opening a link establishes acceptance — supported static contradiction.** Policy lines 3–4 distinguish a view from the named decision maker's explicit acceptance of the displayed version. `implementation.py:1–3` unconditionally writes `accepted` on `open_link`, and `generated-prd.md:6` describes the same behavior. The output's customer-opening-the-link scenario (`output.md:3–5`) follows directly. The function has no actor or explicit-accept input/check. This proves the supplied function violates the described behavior; it does not prove the behavior of an unseen authentication or routing layer. The output makes no assertion of observed external exploitation.

2. **Changed amount inherits acceptance — supported static contradiction.** Starting from an accepted proposal, `update_amount` mutates only `amount` (`implementation.py:6–8`), preserving its status. `generated-prd.md:6–7` confirms the current amount is treated as accepted. This conflicts with policy lines 4–6 requiring a fresh decision for changed terms and retaining the previous decision in its history. `output.md:7–9` ties the finding to that exact path. It correctly treats absent version/history handling as absent from the provided code and explicitly leaves the unprovided delivery-date path unverified. The recommendation to bind acceptance and history to the relevant version implements an adopted rule, not an invented new policy.

3. **Readiness and test oracle — supported evidence critique.** `generated-prd.md:8` declares verification while `test_acceptance.py:1` says no run log/current result is supplied. Lines 5–6 expect immediate acceptance on link opening, which conflicts with policy lines 3–4 even if the test passed. `output.md:11–13` correctly separates test existence, policy fidelity, and actual execution. It does not claim a test failure was observed, and its final static-review/no-execution statement at line 15 matches the captured calls.

No runtime execution is needed for these assignment and authority contradictions. The supplied files do not prove actual customer behavior, successful remediation, complete application authorization, or delivery-date implementation.

## 07: workspace boundaries, retry identity, and reachable recovery

**Scope and authority are correctly bounded.** The intended boundaries are in `product-notes.md:3–21`; adapters are excluded, and in-memory dictionaries explicitly stand in for shared durable stores (`product-notes.md:23–26`). The output does not infer loss of persistence from Python dictionaries. Support design, CSV, and meeting material (`support-handoff.md:3–10`) is unrelated to the raw request's access/repetition/recovery scope and correctly stays out of the findings.

1. **Cross-workspace disclosure through ID and key — supported static defect.** An active B session passes `_require_member` (`implementation.py:18–20`). `get_export` then returns the job by ID without checking its workspace (lines 47–49), and `_view` includes workspace, filters, state, and location (lines 22–29). The alternative request path looks up a globally indexed key and returns its job before considering B's workspace (lines 31–34). Both violate the explicit cross-workspace prohibition, including known IDs/reused keys (`product-notes.md:3–7`). The output's A/B scenarios and checks (`output.md:5–12`) stay at workspace ownership; they do not invent a per-individual ownership requirement within a workspace. Existing inactive-membership rejection and session-derived new-job workspace (lines 32,37) do not repair either return path.

2. **Queue failure followed by browser retry — supported, with a stated failure precondition.** A push that raises before accepting its message leaves the job and key stored because lines 42–43 precede line 44. Product notes line 18 maps `RuntimeError` to 503. A same-key retry returns at lines 33–34 and never republishes. No recovery scheduler is supplied. This is a valid one-queue-outage scenario under the promised recovery in notes lines 14–16. `output.md:17` explicitly states the before-acceptance precondition; it does not assume every queue exception means non-delivery. The proposed original-ID recovery and separate successful-acceptance/lost-response check (lines 19–21) correctly preserve one logical export without prescribing an adopted retry mechanism.

3. **Timeout or worker interruption has no scheduled continuation — supported within the supplied flow.** Notes lines 18–20 make queue delivery at most once, remove the message on `take`, and exclude automatic requeue after worker failure, while preserving access to the shared job store on restart. The worker marks `running` before rendering and `failed` on timeout (`implementation.py:55–60`). Repeating the browser submission merely returns the stored job (lines 33–34). A manual second `run_export` could retry a non-complete job, but that method's callable existence is not a recovery trigger. The output correctly distinguishes that capability from a reachable scheduled/owned recovery path (`output.md:23–30`). The interruption-after-`running` scenario is within the raw request's interrupted-export scope (`request.md:4–5`); it does not require assuming process-local stores. Actual restart behavior, abandonment timing, and the eventual recovery mechanism remain untested engineering choices.

4. **Non-complete download visibility — correctly conditional, not established external exposure.** `_view` returns location without a completion guard (lines 22–28); the worker writes location before state becomes complete (lines 61–62). Thus the sequential snapshot admits a location/state mismatch. A read between writes or durable interruption makes that mismatch relevant only if the adapter exposes it; an atomic transaction could remove the window. `output.md:35` explicitly preserves that uncertainty, as required by notes lines 23–26 excluding storage adapters. Its proposed non-complete-state guard and check (lines 37–39) are bounded by notes lines 20–21. A timed-out renderer's temporary object alone is not proof of leakage: the timeout path does not assign a returned location. The output presents that as a future check rather than an observed leaked object.

5. **Same key with changed filters — current behavior supported; conflict policy still a proposal.** Within a workspace, using the same key for August then September returns the original job before inspecting new filters (lines 33–38). Notes lines 9–12 specify retry identity for the same operation, not the response policy for changed-content reuse. `output.md:41–48` correctly calls for an explicit decision and labels rejection/conflict as a proposed resolution with conditional checks. Its claim that the UI *may* associate the response with September is a possible consequence, not source evidence that a supplied UI actually does so. Exact duplicate retries and independent keys across workspaces are already adopted requirements; changed-content rejection is not.

The test coverage summary (`output.md:50`) matches the three source tests at `test_existing.py:16–35`: sequential identical requests, own-workspace completed status, and inactive creation rejection. The complete-job guard at implementation lines 53–54 supports avoiding regeneration by deliveries beginning after completion, not arbitrary concurrent-worker safety. `output.md:52` correctly leaves concurrent store atomicity unverified. A hold recommendation is a review judgment based on the static access/recovery defects, not an observed runtime pilot outcome.

## 10: assigned actors, immutable revisions, and ledger truth

**The adopted policy is available and used.** The plan links it at `reservation-confirmation-plan.md:3–5`; its adopted status is stated at `policy/offer-acceptance.md:3–4`. These documents describe a proposed flow, not an implemented executable. `output.md:3,70` correctly limits the review to documented behavior and says no implementation/runtime verification occurred. The community notice expressly excludes exhibition accounts from the pilot (`community-notice.md:5–6`) and adds no reservation rule.

1. **Non-organizer acceptance — supported plan contradiction.** The plan's step 1 checks active membership and reservation workspace only (lines 17–20), then inserts a member's acceptance after current-revision validation (lines 21–26). It expressly states no organizer assignment check (lines 28–30). Policy lines 10–13 grant acceptance only to the assigned organizer and explicitly deny manager substitution. An active other member or manager in the same workspace submitting the current revision therefore passes the proposed flow. `output.md:5–15` correctly preserves inactive/cross-workspace denials and fixes the missing assigned-actor check before any successful acceptance/retry return. There is no need to assume an authentication defect or cross-workspace bypass to make this scenario reachable.

2. **Revision-blind repeats — supported plan contradiction with two distinct cases.** The existing-row lookup uses member/reservation and precedes revision validation (plan lines 21–22); the table has one such row and publishing a later revision does not update it (lines 28–30). Policy lines 6–8 make changed offers distinct immutable revisions; lines 15–19 require specific-revision agreement, one logical action for an exact retry, and an explanation for a superseded request. After a successful R1 acceptance, a reviewed R2 request returns stored R1 instead of recording R2. Separately, after an R1 timeout, the documented client retains/retries its R1 payload (plan lines 10–13); if R1 was committed and R2 is then published, that retry bypasses superseded-revision rejection. These are the scenarios at `output.md:23`; they follow the supplied client/server rules rather than assuming the client silently switches payloads. The stale-timeout variant needs an existing R1 row; a timeout before commit would instead reach revision rejection, a limitation implicit in the output's accepted-R1 setup. Checks at lines 29–32 correctly separate still-current retries, superseded payloads, and new explicit R2 agreement. Physical schema choice remains engineering work, not a new policy decision.

3. **Acceptance committed but publication interrupted — supported missing recovery path.** Plan lines 25–26 commit acceptance before publication and can return 503; lines 35–36 retain no event on failed publication and provide no scheduled publisher. The existing-row retry returns success before the publish step (lines 21–22). Operators can inspect but have no repair action (lines 39–40). A failure/interruption before successful delivery therefore leaves a stored acceptance without any supplied path to ledger application. Consumer event-ID deduplication at lines 34–35 cannot create an undelivered event. `output.md:34–44` correctly ties recovery to the same logical acceptance and permits multiple mechanism choices. “Permanently disconnected”/“never receives” should be read within the described flow and the non-delivery scenario, not as proof that every ambiguous publisher error means no delivery or that unknown external operations can never repair it. The explicit pre-publication interruption check at line 44 makes the failure case concrete.

4. **Premature room-secured status — supported independently of delivery recovery.** The status endpoint reads an `accepted` row and labels it secured (plan lines 36–37), while actual allocation is performed by the consumer (lines 34–35). Policy lines 21–23 explicitly make the ledger authoritative and require a visible received/secured distinction. Successful queue publication followed by consumer delay is sufficient; publication failure can prolong the mismatch. The correction/checks at `output.md:46–56` follow an existing adopted state rule. Unknown storage or queue implementation does not turn the already described status-source contradiction into an undecided product requirement.

5. **Pending withdrawal — correctly retained as an owned unknown.** Both policy lines 25–27 and plan lines 39–42 say this outcome is undecided and the endpoint/criteria are unwritten. `output.md:58–68` does not choose allocation, suppression, or release. It requests an operations decision before inclusion and makes checks conditional. The withdraw-versus-apply scenario is a future decision exercise, not a reachable demonstrated defect in an existing withdrawal implementation. No automatic release is authorized by the supplied policy.
