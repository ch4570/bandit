I recommend holding the two-workspace pilot until access isolation and recovery are corrected and verified. The findings below come from static inspection, not observed execution.

1. **Cross-workspace access is possible through both lookup paths.** Product notes lines 3–7 prohibit exposing another workspace’s status, filters, or download location. In `implementation.py:31–34`, request keys are global: if workspace B submits a key already used by A, B receives A’s export view. At lines 47–49, an active B member knowing A’s export ID can retrieve that same view without a workspace check.

   **Smallest fix/check:** Scope request-key lookup to the authenticated workspace and check ownership before returning any export view. Verify that identical keys in A and B create distinct exports; B cannot read A’s export by ID; neither path exposes A’s filters, status, or location. Retain inactive-member denial and check it on retrieval too.

2. **Reusing a key with changed filters has no agreed meaning.** Product notes lines 9–12 define retries of the “same operation,” but do not define changed-content reuse. `implementation.py:33–34` silently returns the original export regardless of supplied filters. A member requesting August, then September under the same key, receives August’s export and may mistake it for September’s.

   **Smallest decision/check:** Define operation identity within the workspace. I recommend treating the same key with equivalent filters as a retry and rejecting changed filters with a clear conflict, leaving the original job unchanged. Specify whether another member in the same workspace may retry that operation. Check exact retries, changed filters, and the chosen cross-member rule. This is a proposed policy, not an existing requirement.

3. **A queue outage strands an accepted export.** Product notes lines 14–19 require recovery without a different logical export and specify that `RuntimeError` becomes HTTP 503. In `implementation.py:42–44`, the job and key are saved before queue submission. If submission fails before delivery, the client gets 503; retrying returns the saved pending job at lines 33–34 without submitting it again. No recovery path is supplied.

   **Smallest fix/check:** Retain recoverable dispatch state and provide a retry or reconciliation path that schedules the existing job. Simulate one failed queue submission followed by recovery and an identical client retry; require the same export ID to reach completion. Also check the uncertain-acknowledgement case where submission was accepted before an error, so recovery does not create another logical export.

4. **Renderer failure or worker interruption has no demonstrated recovery trigger.** Queue delivery removes the message and failures are not requeued (`product-notes.md:18–21`). A timeout marks the job failed and raises (`implementation.py:55–60`); a process interruption can leave it running. Submission retries merely return those states. Although calling `run_export` again could retry rendering, nothing supplied arranges that call.

   **Smallest fix/check:** Add a bounded recovery path for failed and abandoned running jobs, preserving their IDs. Check one renderer timeout followed by success, and interruption after message removal followed by restart with the same store. Both must complete without a new export. Deliver a completed job again and assert no additional renderer call; lines 53–54 already provide a sequential completion guard, but existing tests do not verify it.

5. **Download visibility is not enforced by completion state.** Product notes lines 20–21 allow temporary renderer objects but require only completed jobs to expose locations. `implementation.py:61–62` assigns the location before marking completion, while `_view` returns it unconditionally at line 28. If reads or interruption can occur between those writes, a running job can expose a location.

   **Smallest fix/check:** Gate returned locations on `state == "complete"` or establish an atomic completion update. Check a persisted noncomplete job containing a location and require the response to hide it. Adapter atomicity is unavailable, so the intermediate-state scenario is conditional.
