# Slotlet 일정 변경 개발 명세

채택된 운영 정책을 기준으로 한다. **새 시간 확정과 기존 시간 해제가 함께 성공하기 전까지 원래 확정 예약은 유지한다.** 미승인 초안의 선취소, 브라우저 타이머 기반 승인, 오류 시 무조건 재시작은 채택하지 않는다.

지원 기록은 화면 walkthrough 관찰이며, 구현이나 테스트로 검증된 결과가 아니다.

## 현재 구현할 동작

1. 로그인한 예약 소유자가 예약 상세에서 ‘일정 변경’을 선택한다. 서버가 소유권과 변경 가능 시간을 검사한다. 기존 예약 시작까지 24시간 이상 남아 있어야 한다.
2. 같은 스튜디오의 다른 60분 슬롯 중 예약 가능한 시간을 보여준다. 조회만으로는 홀드하지 않는다. 기존 확정 예약은 계속 유효하다.
3. 고객이 시간을 선택하면 서버가 가용성을 다시 확인하고 2분 홀드를 생성한다. 홀드는 해당 물리적 스튜디오의 겹치는 시간대를 다른 고객의 홀드·예약에서 제외한다. 기존 확정 예약과 겹치는 후보는 제공하지 않는다.
4. 화면에 기존 예약, 변경 후보, 홀드 만료 시각을 표시한다. 사용자에게 표시하는 시각에는 날짜와 Asia/Seoul을 명시한다. 카운트다운은 안내용이며 승인 여부는 서버 시각으로 판단한다.
5. ‘변경 확정’ 시 서버가 소유권, 변경 가능 시간, 예약 상태, 홀드 소유권·유효성을 재검사한다. 새 슬롯 확정, 기존 슬롯 해제, 선결제 이용권 승계를 하나의 원자적 변경으로 처리한다. 일부만 성공한 상태는 허용하지 않는다.
6. 성공이 확인되면 확정된 새 예약을 표시한다. 실패·만료 시 기존 예약을 유지하고 원인을 안내한다. 명시적 취소가 성공한 경우는 별도이다.

## 작은 미정 규칙에 대한 추천 초안

- **경계:** 변경은 서버 시각이 기존 시작 시각의 24시간 전과 같을 때까지 가능하다. 홀드는 생성 시각부터 120초이며 `현재 시각 < 만료 시각`일 때만 유효하다. 만료 시각과 같으면 무효다. 만료 정리 작업 지연과 관계없이 이후 요청은 슬롯을 다시 확보할 수 있다.
- **다중 탭:** 소유자당 활성 변경 홀드는 하나만 허용한다. 다른 후보를 선택하면 새 후보 확보와 이전 홀드 해제를 함께 처리한다. 확보 실패 시 이전 홀드는 원래 만료까지 유지한다. 동일 후보 재선택은 만료를 연장하지 않는다.
- **오래된 화면:** 요청은 기준 예약 버전과 홀드 식별자를 포함한다. 다른 탭이 홀드를 바꾸거나 예약을 변경·취소했다면 이전 요청은 거절하고 최신 예약·홀드 상태를 표시한다. 조용히 다른 후보를 확정하지 않는다.
- **중복·통신 오류:** 확정 의도마다 재사용 가능한 요청 식별자를 둔다. 같은 요청 재전송은 동일 결과를 반환하며 예약이나 이용권을 중복 생성하지 않는다. 응답이 끊기면 ‘결과 확인 중’을 표시하고 서버에서 요청 결과와 현재 확정 예약을 조회한다. 재접속·새로고침 후에도 예약 상세에서 실제 상태를 확인할 수 있어야 한다.
- 화면에서 나가면 홀드를 해제하며, 해제 요청이 도착하지 않아도 서버 만료를 적용한다. 일반 취소와 변경 확정이 경합하면 하나만 먼저 반영하고 다른 요청은 최신 상태를 반환한다.

## 수용 시나리오

| 조건·행동 | 기대 결과 |
|---|---|
| 소유자가 유효한 홀드로 변경 확정 | 새 예약만 확정되고 기존 시간은 풀리며 이용권은 한 번 승계된다. |
| 조회만 하거나 후보 선택 후 이탈 | 조회는 재고에 영향이 없다. 이탈·만료 후에도 기존 예약은 유효하다. |
| 비소유자 요청 또는 24시간 경계 이후 요청 | 서버가 거절하며 예약은 바뀌지 않는다. 경계 정확히 시점은 허용한다. |
| 두 고객이 겹치는 후보를 동시에 확보 | 최대 하나만 홀드에 성공한다. 일반 예약도 같은 재고 제약을 적용받는다. |
| 유효 홀드 중 다른 고객이 확보 시도 | 거절된다. 만료 정확히 시점에는 재확보 경쟁이 가능하며 중복 확정은 없다. |
| 브라우저에는 시간이 남았지만 서버에서 만료 | 확정 거절, 기존 예약 유지, 후보 재선택 안내. |
| 탭 A 선택 후 탭 B가 후보 변경, A가 확정 | A의 오래된 홀드 요청을 거절하고 최신 상태를 보여준다. |
| 변경 도중 저장 실패 | 새 확정과 기존 해제가 모두 반영되지 않고 기존 예약이 유지된다. |
| 확정 응답 유실 후 재시도·재접속 | 실제 결과를 복구한다. 성공했다면 새 예약 하나, 실패했다면 기존 예약을 보여준다. |
| 일반 취소와 변경 확정 동시 요청 | 하나만 반영되고 다른 요청은 최신 상태를 확인한다. |

## 범위와 일정

결제·환불·반복 예약·캘린더 연동·신규 계정 시스템은 제외한다. 개발자 1명, 5일은 목표이며 확정 견적이 아니다. 착수 시 기존 취소 서비스와 원자적 변경의 통합 가능성, 공통 재고 제약, 중복 요청·결과 복구 저장 방식을 확인하고 재산정한다. 동시성·복구 검증이 완료되어야 출시할 수 있다. 본 문서에서는 구현이나 제품 테스트를 수행하지 않았다.
